# 游戏机制与玩法策划工作流

状态：draft；配合 [角色指令](../agents/gameplay-designer.md) 和 [策划包模板](../assets/gameplay-design-brief.template.md) 使用。此文是人工可读参考流程，不新增机器 Gate、Contract schema 或 Registry 状态。

## 使用入口

在任务中引用角色文件，例如：

```text
请读取 game/game-production-pipeline/agents/gameplay-designer.md，按该角色开展本次策划。
输入：我的现有玩法资料和本次要解决的问题。
约束：目标玩家、操作方式、原型时间及不能改变的规则。
先给机制方案与推荐，再把指定或已授权的方向写成规则和最小原型任务书。
未发生的试玩请标为待验证，输出到我指定的项目目录。
```

这是当前任务的角色使用方式，不会安装具名 Agent。需要持久项目岗位时，将角色内容及其引用的方法/模板映射进 [`project-agent-preset.template.md`](../assets/project-agent-preset.template.md)，指定文件所有权，在已批准的组织、Preset 和 Skill Binding 下调用现有生成器。项目锁记录的插件版本必须实际包含此模板；已安装旧发布版不会自动包含仓库新文件。

小型项目由 `AGT-GD` 兼任；持续承担多个机制迭代且值得隔离上下文时，再按项目现有编制流程设独立岗位。正式 Pipeline Contract 使用已支持的 `SPECIALIST` 槽位绑定获批准的岗位，不把模板 ID 加入默认 Agent 枚举。

## 推进与退回

“自动检查”只指当前环境已有工具能够执行的确定性检查；缺少对应工具就列为待人工复核，不能声称有专用校验器。人类对方向的既有授权可作为验收依据，日常规则细化不重复询问。

| 节点 | 准入与输入 | 输出 | 自动验证（有工具时） | 人工/专业验收与退出条件 | 失败退回 |
|---|---|---|---|---|---|
| 问题界定 | 用户提出策划问题，读取已有简报与范围 | 事实/假设/缺口、体验目标、最大风险 | 文件存在、引用版本可解析 | 用户或 `AGT-GD` 确认方向和限制；已有确认直接消费 | 关键方向缺失或矛盾 → 用户；可继续独立研究 |
| 研究与方案 | 问题明确，或有明确标记的探索假设 | 来源记录、差异方案、推荐与代价 | 本地链接与资料路径有效 | 探索材料可交付；进入具体选向需有效决定或既有授权 | 换皮方案 → 重做比较；未查证 → 保留未知 |
| 规则规格 | 已指定方向，或用户授权制作明确标记的候选规格 | 策划包、稳定 ID、状态/参数、依赖 | 可计算的公式、概率和可复现推演 | `AGT-GD` 检查整体一致性，实现者确认无需补发明规则；仍为候选时不得当作批准基线 | 矛盾/漏规则 → 本角色；跨范围 → 人类 |
| 原型任务 | 关键规则足够明确，有预算和实施授权 | 最小实验、用例、观察项及任务交接 | 已有用例格式、资源引用及工程检查 | 实现者确认可实施，QA/体验负责人确认实验能检验假设 | 超预算 → 缩小范围或人类；不可测试 → 改实验 |
| 试玩与评审 | 已有指定 revision/build 的原型与适合的参与者 | 原始观察、解释、证据限制、保留/修改/删除建议 | 工程测试和数据一致性 | QA 独立记录结果；人类判断目标体验和 GATE-1；无试玩只能交付任务书 | 工程错误 → 实现者；理解/反馈 → 内容或 UI；机制失效 → 本角色 |
| 修订与交接 | 有有效结论或授权的修改要求 | 新 revision、影响清单、过期证据、复测任务 | 引用版本与现有工程回归 | 责任人接收；必要人工判断已记录，预算内继续迭代 | 证据与版本不匹配 → 补测；方向变更 → 用户/`AGT-GD` |

## 可交付的三个边界

1. **探索包完成**：研究、选项、推荐、缺口齐备；不要求伪造项目方向或试玩。
2. **原型策划完成**：规则、参数假设和实验可执行；明确尚未验证的体验风险。
3. **体验评审完成**：真实试玩证据与当前版本一致，人工结论明确；文档/脚本检查通过不能替代此阶段。

这些是交付范围，不是新增运行时状态。接入已有循环时，由项目经理将产物引用纳入中心依赖清单及相应 Loop 的输入/输出，并沿用已有审批、授权和 Registry 机制。
