# 游戏制作多 Agent 架构 v0.1

状态：`draft-approved-direction`

本架构面向所有游戏项目，采用可复制、可裁剪、可特化的通用根框架。根框架覆盖游戏制作的完整流程，但不写死具体游戏的玩法、内容、验收阈值或项目事实。复制或安装到具体项目后，通过项目配置、模块选择和覆盖层完成特化；项目特有内容不得反向成为通用核心的默认规则。

引擎能力属于适配范围：通用层描述职责、交接、审批和产物，适配内容负责把通用要求映射到 Godot、Unity 或其他生产环境。当前只实现 Godot 适配内容。

## 已批准的根框架原则

- 适用范围是所有游戏项目，而不是当前用于验证的两个项目。
- 根框架负责提供完整流程、公共契约和扩展位置，不提供某个游戏的固定答案。
- 项目实例可以裁剪不需要的模块，并对 Agent、Skill、Workflow 和 Contract 进行项目级特化。
- 项目专属规则、素材、版本、构建哈希和测试阈值属于项目实例或隔离的验证记录，不得成为通用核心的默认要求。
- 真实游戏项目只用于检验框架的复用性与边界，不决定框架只能服务于这些项目。

## 四层模型

| 层 | 回答的问题 | 典型内容 |
|---|---|---|
| Agent | 谁长期承担判断、协调或交付责任 | 游戏设计、内容设计、Godot 实现、测试发布 |
| Skill | 一个角色如何稳定完成某项重复工作 | 提取核心循环、编写关卡简报、定义交互状态机 |
| Workflow | 多个角色按什么顺序协作，失败退回哪里 | 垂直切片、新关卡、试玩修订、版本发布 |
| Contract | 各步骤交换什么，怎样证明完成 | 输入、输出、稳定 ID、检查、人工闸门、回退规则 |

P0～P9 是生产阶段，不默认等于十个 Agent。只有同时满足以下条件，才把职责提升为常驻 Agent：

- 需要持续保留独立判断边界；
- 会跨多个工作流反复出现；
- 拥有清晰且不重叠的产物所有权；
- 独立角色能降低风险或上下文污染；
- 不能仅靠模板、脚本或短时专业能力完成。

重复执行至少两次且步骤稳定后，才把工作方法提取为 Skill。

## 常驻 Agent

| ID | Agent | 阶段所有权 | 核心职责 |
|---|---|---|---|
| `AGT-DIR` | 管线统筹 Agent | X0 | 路由任务、维护依赖与状态、执行闸门，不替代领域判断 |
| `AGT-GD` | 游戏设计 Agent | P0、P1 | 项目范围、核心体验、核心循环、玩家行为和系统规则 |
| `AGT-CD` | 内容设计 Agent | P2、P4、P5 | 叙事骨架、关卡职责、交互规格和资产需求 |
| `AGT-GODOT` | Godot 实现 Agent | P3、P7 | 技术架构、预置场景与节点、功能实现、集成和工程验证 |
| `AGT-QA` | 测试发布 Agent | P8、P9 | 独立验收、问题分类、回归、构建和发布证据 |

详细边界见 `agents/`。

## 按需专业能力

P6 内容资产生产不设置为单一常驻 Agent。环境美术、角色与动画、UI/UX、VFX、音频、本地化的工具链和验收方式差异较大，应由 `AGT-DIR` 根据 `AGT-CD` 产出的资产需求单调度对应专业 Agent 或 Skill。

专业执行者必须遵守以下边界：

- 只消费已批准的资产需求和技术规格；
- 不自行改变游戏机制、关卡目标或叙事事实；
- 产出源文件、运行时文件、导入结果和使用许可信息；
- 由内容设计检查表达是否符合意图，由实现 Agent 检查引擎与性能规格，由测试 Agent检查集成结果。

## 阶段与角色映射

| 阶段 | 主责 | 必要协作 |
|---|---|---|
| P0 项目定义与范围 | `AGT-GD` | `AGT-DIR`、人类 |
| P1 核心玩法与系统 | `AGT-GD` | `AGT-GODOT` 提供可行性证据 |
| P2 剧情与叙事 | `AGT-CD` | `AGT-GD` 检查玩法与主题一致性 |
| P3 技术架构与工具 | `AGT-GODOT` | `AGT-DIR`、`AGT-QA` |
| P4 关卡设计 | `AGT-CD` | `AGT-GD`、`AGT-GODOT` |
| P5 交互规格 | `AGT-CD` | `AGT-GD`、`AGT-GODOT` |
| P6 内容资产生产 | 按需专业 Agent | `AGT-CD`、`AGT-GODOT` |
| P7 功能实现与集成 | `AGT-GODOT` | 按需专业 Agent |
| P8 试玩、测试与平衡 | `AGT-QA` | `AGT-GD`、`AGT-CD`、人类 |
| P9 构建与发布 | `AGT-QA` | `AGT-GODOT`、人类 |
| X0 任务、文档与变更 | `AGT-DIR` | 全体角色 |

## 决策权限

Agent 可以在已批准规格内选择实现方法、生成结构化产物、执行检查和提出修订。以下决定必须由人类批准：

- 项目范围、核心支柱和 `MUST / SHOULD / WON'T`；
- 核心玩法是否值得继续；
- 角色、情绪、节奏、美术方向是否达到目标；
- 灰盒是否冻结并进入高成本内容生产；
- 是否接受破坏性变更、延期、降级或删减；
- 是否允许发布构建成为对外版本。

## 事实源与变更规则

- 已批准的 Contract 和决策记录是工作的事实源，聊天内容不能直接覆盖它们。
- Agent 发现上游矛盾时必须停止受影响步骤，提交变更请求，不得在下游静默修正规格。
- 所有重要对象使用稳定 ID；改名不改 ID，删除保留迁移说明。
- 交接必须附带变更文件、验证证据、风险和未解决问题，不能只说“已完成”。
- 失败必须按 Contract 的回退规则返回负责角色；不得由下游角色越权重写上游决定。

## 适配层边界

通用层只描述玩家体验、内容意图、系统责任、验收和交接。引擎节点、资源类型、脚本语言、导入规则和执行命令属于适配层。

当前 Godot 适配层必须遵守“预置节点优先”：能够在编辑器中稳定表达的节点树、UI、碰撞、动画、相机和关卡结构，应序列化到 `.tscn` 或 `.tres`，不通过运行时脚本临时搭建。

## 第一版验证策略

先用一个 10～15 分钟垂直切片验证：

- 一个核心玩法；
- 一个剧情节点；
- 一个小关卡；
- 三到五种交互对象；
- 一套简单 UI；
- 一次存档读档；
- 一个可导出的构建。

只有垂直切片暴露出的重复步骤，才进入 Skill 候选清单。
