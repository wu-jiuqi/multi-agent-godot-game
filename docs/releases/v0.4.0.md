# v0.4.0 — 项目经理启动模式与中文编码回归保护

## 版本定位

`v0.4.0` 在项目初始化与组织设计之间增加项目文档基线。项目所有者先提供已规划的玩法、美术方向、大致实现方案与约束；项目经理启动工作流负责结构化、追溯、区分事实与假设、发现缺口，并生成供项目编制设计 Agent 使用的责任需求。

本版本同时修复 Windows PowerShell 5.1 中文读取兼容指引并增加编码回归保护。修复发生在插件规范、生成器、校验器、测试和发布包层；它不会改变 PowerShell 5.1 的默认文件读取编码，也不会重写现有游戏项目。

## 新增内容

- 新增第六个核心 Skill：`$prepare-game-project-brief`；
- 新增项目经理受限启动模式，正式编制获批前不伪造 Position 或 Agent Instance；
- 新增 `game-production-project-brief/v1` 契约、示例和确定性校验器；
- 新项目 bootstrap 自动创建 `game-pipeline/project-definition/project-brief.yaml` blocked 草案；
- 项目结论显式区分 `confirmed / preference / hypothesis / unknown`，非未知结论必须引用登记来源；
- 项目简报只有 staffing-ready、摘要匹配且拥有人类审批记录时才能进入组织设计；
- 项目编制设计 Agent 改为消费责任需求，不允许在简报未确认时猜测项目方向；
- 项目实例总校验器同时检查项目简报、外部审批记录和摘要新鲜度；
- 新增项目启动与编制准入工作流文档；
- README 明确自然语言优先，插件命名空间长名只用于强制路由和发现性测试。

## 中文编码修复

- 明确插件源码、Markdown、YAML、JSON、TOML、Python、文本模板、bootstrap 生成文件和发布 ZIP 内文本统一为 UTF-8 无 BOM；
- 保持生成器显式使用 UTF-8/LF，不为兼容 PowerShell 5.1 全量增加 BOM；
- 新增只读 `validate_text_encoding.py`，严格解码文本并拒绝 BOM、`U+FFFD`、缺失的代表性中文和损坏的 managed block 摘要；
- 新校验器与构建器输出 ASCII-safe JSON，避免代码页 936 破坏自动化结果；
- 项目编码校验同时检查 plugin lock 版本和 framework digest 为 `normal`；
- 新增确定性 `build_release.py`，按原始字节打包，不在构建过程中转码；
- 发布 ZIP 复用同一编码规则，并生成可回读验证的 SHA-256 sidecar；
- 新增 bootstrap apply/readback/幂等、中文 README、初始 Change Set、managed block、Agent TOML 和 ZIP 回归测试。

根因不是模板损坏，而是 Windows PowerShell 5.1 的无参数 `Get-Content` 可能使用本地 ANSI 代码页读取无 BOM UTF-8。读取中文文件时使用：

```powershell
Get-Content -LiteralPath "文件路径" -Encoding UTF8
```

`chcp 65001` 只调整控制台代码页，不保证 `Get-Content` 使用 UTF-8。PowerShell 7 或明确配置为 UTF-8 的编辑器一般可以直接读取。看到乱码时应先按 UTF-8 重新读取，不要覆盖 managed block、`plugin-lock.yaml` 或批量转码现有项目。

## 启动流程

1. `$bootstrap-game-pipeline` 建立控制面、空组织和 blocked 项目简报草案；
2. 项目所有者提供核心玩法、美术方向、大致实现方案、范围约束、已有资料与明确未知项；
3. `$prepare-game-project-brief` 以项目经理启动模式整理项目文档基线；
4. 项目所有者批准精确简报摘要；
5. `$design-game-organization` 生成团队方案、Agent Presets、Skill Bindings 与组织图；
6. 项目所有者批准编制后才生成正式 Codex Agent 适配器并进入生产。

项目简报是编制输入包，不是最终 GDD。编制获批后，游戏设计、美术、内容、技术和 QA 等角色分别深化自己的专业文档。

## 审批与失败边界

- 项目经理可以整理表达、建立来源索引、标记未知项、识别矛盾、记录风险并追问缺口；
- 项目经理不能把偏好或待验证实现思路改写成已确认事实；
- 任何会新增玩法、美术、范围、预算、平台或技术方向的缺口都返回项目所有者；
- 项目简报内容变化会改变 `subject_digest`，旧审批不得继续使用；
- 组织设计不能把责任需求静默解释为指定 Agent，仍须形成待审批 Change Set；
- 编码校验只报告问题，不自动修改或转码任何源文件、managed block 或项目锁。

## 现有项目隔离

现有游戏项目不需要因为 PowerShell 显示乱码而重新初始化。它们的模板和 YAML 若能严格按 UTF-8 读取，内容就没有损坏。

The Nameless Vessel 当前锁定 `0.3.0-alpha.1+codex.20260814152940`。本次源码升级不修改该项目的 `plugin-lock.yaml`、Registry、Agent Preset、Skill Binding 或任何游戏内容。`D:\A Cat in Fleeting Light` 也只作为已知事实参照，不执行修复、重新初始化、managed block 改写或批量转码。

本版本尚未提供 `v0.3.0-alpha.1 → v0.4.0` migrator，因此旧项目继续进入 `read_only`；不得手工修改项目锁或复制新文件伪装迁移。

## 当前限制

- Windows PowerShell 5.1 的无参数 `Get-Content` 仍可能按 ANSI 读取；本版本提供明确指引和回归防线，不修改 PowerShell 自身行为；
- `validate_text_encoding.py` 能识别非法 UTF-8、BOM、`U+FFFD` 和受保护代表性文本缺失，但不能可靠识别所有“先错误解码、再保存为合法 UTF-8”的任意 mojibake；关键生成文本通过精确原文断言补足；
- 项目简报批准目前仍由 Skill、文件契约和校验器协作，没有 MCP 或 Hook 阻止所有手工绕过；
- 尚未提供项目简报的可视化编辑器；
- 尚未提供 v0.3 到 v0.4 的迁移器；
- 只有 Godot 适配层，Unity 和其他引擎尚未验证。
