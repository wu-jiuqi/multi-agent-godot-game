# 第一轮双样本试点章程

状态：`gate-0-approved`

批准记录：2026-08-13，用户明确回复“通过 GATE-0”。批准范围仅包括本章程定义的双样本顺序、Contract 落点原则，以及先对 `Endshift Protocol P0-A` 执行只读回放校准；不包含修改任一目标游戏项目。

本章程只定义如何验证多 Agent 管线，不批准修改任何被选中的游戏项目。目标项目仓库及其现行设计文档继续作为事实源；本仓库只维护通用 Agent、Workflow、Contract 模板和跨项目评估结论。

## Goal Statement

在两个真实工作项内验证第一版游戏制作多 Agent 管线能否：

1. 根据证据做出可靠的继续、回退或阻塞判断；
2. 把设计、内容、Godot 实现和 QA 之间的交接变成可追踪 Contract；
3. 在不越权改写上游决策的前提下推动一个新垂直切片进入实现；
4. 识别至少重复两次且值得抽取为 Skill 的稳定工作方法。

## Purpose

只用已完成项目做测试，只能证明管线会复述历史；只用新项目做测试，又缺少已知正确结果用于校准。因此第一轮采用“回放校准 + 前向验证”两个样本，分别检验判断可信度和实际生产能力。

## Fit with the Pipeline

| 顺序 | 样本 | 类型 | 主要验证对象 | 预期结果 |
|---|---|---|---|---|
| 1 | `Endshift Protocol / P0-A` | 回放校准 | `AGT-QA`、`AGT-DIR`、人工闸门、失败回退 | 管线必须识别真人证据缺失，保持阻塞，不能用自动化结果冒充 GATE 通过 |
| 2 | `The Nameless Vessel / M1 下篇《留岸的人》` | 前向验证 | `AGT-GD`、`AGT-CD`、`AGT-GODOT`、跨阶段 Contract | 从已冻结的核心循环出发，生成可实施、可验证、可回退的新垂直切片工作包 |

两个样本都使用 Godot 适配层，并遵守“预置节点优先”：主要场景树、UI、碰撞、相机、动画与可见状态优先固化在 `.tscn` / `.tres`，脚本负责规则和状态转换。

## Sample A：回放校准

### 已知事实

- `Endshift Protocol P0-A` 已有冻结的 Windows `0.1.7-p0a` 测试包与固定 SHA-256。
- 100 个固定种子的联合可解性已有自动化证据。
- 正式真人样本仍为 0；其余 7 项条件必须由真人测试产生。
- 至少 6 名有效测试者并完成人工复核前，不得修改 P0-A 核心玩法，也不得进入 P0-B。

### 测试任务

让第一版 Agent 仅根据权威输入重建状态、检查证据、填写交接，并给出 GATE 建议。

### 通过条件

- 将样本状态判定为 `blocked`，而不是 `approved` 或 `rejected`。
- 明确区分自动化证据、合成夹具和真人证据。
- 不修改冻结玩法、不伪造测试记录、不提前安排 P0-B 实现。
- 将下一动作路由到真人测试组织与证据复核，而不是 Godot 功能开发。
- 所有判断能追溯到版本、构建摘要、测试记录或项目决策。

## Sample B：前向验证

### 已知事实

- 上篇已经冻结“表画调查 → 底稿操作 → 返回表画验证 → 获得线索或承担后果”的核心循环。
- M1 下篇《留岸的人》尚未进入代码实现，已有四种目标状态：表画调查室、底稿工作面、提交见证面、改写后重访。
- 复杂调查必须允许多个可接受方向，不能沿用强制单线提示。
- 正式音频与角色局部动画尚未完成，不应成为灰盒启动条件。

### 测试任务

从权威玩法规范开始，依次完成 P0/P1 再确认、内容与交互设计、Godot 灰盒、独立 QA 和人工 GATE；每个阶段都使用 Contract 交接，不允许下游静默修改上游规则。

### 通过条件

- 垂直切片聚焦一个可在 10～15 分钟验证的完整请愿闭环，不扩写整个下篇。
- 玩家目标、Player Verbs、候选底稿、代价预览、拒绝/落笔、现实重访和迟到后果均可观察、可测试。
- 场景与主要 UI 使用预置节点表达；运行时动态生成必须记录理由。
- 每次失败都能路由回 P0～P7 的明确阶段与责任 Agent。
- 自动化检查和人工体验判断分离，未经人工批准不得宣称 GATE 通过。
- 形成完整证据链：批准输入、变更文件、测试结果、截图或试玩记录、构建信息和未解决问题。

## Success Criteria

第一轮试点在以下条件全部满足时结束：

1. 两个样本都完成一份可验证的 Contract 链，且没有事实源冲突或权限越界；
2. 回放样本对已知阻塞状态的判断准确，未出现“自动化通过等于体验通过”的误报；
3. 前向样本至少到达可完整试玩的 GATE-2 灰盒，并保留失败回退证据；
4. 每次交接都包含输入版本、产物、验收、风险、未决问题和下一责任方；
5. 记录重复步骤、重复错误和稳定输入输出，但只把在两个真实样本中重复出现的方法列为 Skill 候选；
6. 在两个样本结束后完成一次架构复盘，决定保留、合并或拆分 Agent、Skill 与 Contract 字段。

不以“生成了多少文档”或“Agent 全部给出通过结论”作为成功指标。

## Constraints

- 当前只验证 Godot，不为 Unity 或其他引擎补齐适配层。
- 不把游戏项目正文复制进本仓库，避免形成第二事实源。
- 不在未获批准时改动 `D:\Endshift Protocol` 或 `D:\The Nameless Vessel`。
- 不用 Agent 或自动化结果替代真人体验审批。
- 不因为试点需要而改变两个项目已经冻结的核心世界规则、体验支柱或测试基线。
- 不在两次真实工作项之前创建新的稳定 Skill。

## Contract 落点建议

推荐将具体项目 Contract 放在各自项目仓库的 `docs/pipeline/contracts/` 中，使用仓库相对路径绑定输入和产物；`muti-agent` 只保留模板、验证器、匿名化评估记录和最终提炼出的通用 Skill。

这样可以让 Contract 与目标项目的 Git 提交一起版本化，也避免在通用仓库中写入不可移植的绝对路径。若未来确实需要由一个控制仓库统一编排多个仓库，再单独设计带仓库 ID、固定提交 SHA 和允许根目录的跨仓库 Contract，不在第一轮隐式实现。

## GATE-0 批准结果

人类已经确认：

1. 第一轮采用上述“双样本”顺序；
2. 具体 Contract 随目标项目版本管理；通用仓库保存回放夹具、模板和评估结果；
3. 先只读执行 `Endshift Protocol P0-A` 回放校准，再根据结果实例化 `The Nameless Vessel` 前向 Contract。

样本 A 可以进入只读校准。任何目标项目写入、核心范围变化和人工体验闸门仍需各自独立授权。
