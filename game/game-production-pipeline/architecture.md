# 游戏制作多 Agent 架构 v0.3 Alpha

状态：`codex-plugin-alpha-implemented`

本架构面向所有游戏项目，采用可复制、可裁剪、可特化的通用根框架。根框架覆盖游戏制作的完整流程，但不写死具体游戏的玩法、内容、验收阈值或项目事实。复制或安装到具体项目后，通过项目配置、模块选择和覆盖层完成特化；项目特有内容不得反向成为通用核心的默认规则。

引擎能力属于适配范围：通用层描述职责、交接、审批和产物，适配内容负责把通用要求映射到 Godot、Unity 或其他生产环境。当前只实现 Godot 适配内容。

## Codex 插件映射

通用根框架作为全局 `game-production-pipeline` 插件安装。插件通过六个 Skill 暴露初始化、项目简报准备、组织设计、生产循环、门禁审查和 Godot 适配工作流，但不会直接携带某个游戏的项目答案。

目标项目通过 `game-pipeline/` 保存 Registry、版本锁、审批、绑定、循环和项目 Agent Preset，通过 `.agents/skills/` 保存项目专属方法。只有已批准且摘要匹配的 Preset 才能确定性生成 `.codex/agents/*.toml`；TOML 是运行适配器，不是审批事实源。

初始化只建立空组织基线和编制草案。项目经理、编制设计、部门经理或专项 Agent 都必须在项目分析后进入 Organization Change Set，并由人类决定是否成为长期编制。运行时实例可以在批准的 Position 或有限 Temporary Grant 内动态创建，但必须先登记并保持可见。

## 已批准的根框架原则

- 适用范围是所有游戏项目，而不是当前用于验证的两个项目。
- 根框架负责提供完整流程、公共契约和扩展位置，不提供某个游戏的固定答案。
- 项目实例可以裁剪不需要的模块，并对 Agent、Skill、Workflow 和 Contract 进行项目级特化。
- 项目专属规则、素材、版本、构建哈希和测试阈值属于项目实例或隔离的验证记录，不得成为通用核心的默认要求。
- 真实游戏项目只用于检验框架的复用性与边界，不决定框架只能服务于这些项目。

## 四层模型

| 层 | 回答的问题 | 典型内容 |
|---|---|---|
| Agent | 谁长期承担判断、协调或交付责任 | 游戏设计、内容设计、Godot 实现、测试发布 |
| Skill | 一个角色如何稳定完成某项重复工作 | 提取核心循环、编写关卡简报、定义交互状态机 |
| Workflow | 多个角色按什么顺序协作，失败退回哪里 | 垂直切片、新关卡、试玩修订、版本发布 |
| Contract | 各步骤交换什么，怎样证明完成 | 输入、输出、稳定 ID、检查、人工闸门、回退规则 |

P0～P9 是生产阶段，不默认等于十个 Agent。只有同时满足以下条件，才建议把职责提升为项目中的独立 Agent：

- 需要持续保留独立判断边界；
- 会跨多个工作流反复出现；
- 拥有清晰且不重叠的产物所有权；
- 独立角色能降低风险或上下文污染；
- 不能仅靠模板、脚本或短时专业能力完成。

重复执行至少两次且步骤稳定后，才把工作方法提取为 Skill。

## 默认参考编制

下列五个 Agent 是根框架提供的开箱即用参考编制，不是所有项目必须保持不变的固定组织结构。它们的作用是给小型或尚未完成项目特化的团队提供一套职责覆盖完整的默认起点。

表中的 `AGT-*` 是参考 Agent 文档的模板标识，不是项目运行时的 Position ID 或 Instance ID。

| ID | Agent | 阶段所有权 | 核心职责 |
|---|---|---|---|
| `AGT-DIR` | 项目经理 Agent | X0 | 协调跨部门优先级、依赖、资源、进度、交接与冲突，不替代领域或人工判断 |
| `AGT-GD` | 游戏设计 Agent | P0、P1 | 项目范围、核心体验、核心循环、玩家行为和系统规则 |
| `AGT-CD` | 内容设计 Agent | P2、P4、P5 | 叙事骨架、关卡职责、交互规格和资产需求 |
| `AGT-GODOT` | Godot 实现 Agent | P3、P7 | 技术架构、预置场景与节点、功能实现、集成和工程验证 |
| `AGT-QA` | 测试发布 Agent | P8、P9 | 独立验收、问题分类、回归、构建和发布证据 |

详细边界见 `agents/`。

可选专项模板 [游戏机制与玩法策划 Agent](agents/gameplay-designer.md) 负责被委派机制的方案比较、规则规格、数值假设与原型验证设计。`AGT-GD` 保留 P0/P1 整体一致性和系统目录责任，具体机制事实源只设一个写入 owner。小项目可兼任，独立岗位需按项目编制批准；机器 Pipeline Contract 使用已有 `SPECIALIST` 槽位，不新增默认 Agent 枚举。方法、模板与交接见 [玩法策划工作流](workflows/gameplay-design.md)。

## 项目专属编制规则

具体项目可以根据玩法、内容规模、视觉管线、技术风险和团队分工，对默认编制执行以下操作：

- 拆分：把一个默认 Agent 的职责拆成多个专项 Agent，例如将内容设计拆为叙事、关卡、环境美术和交互件美术；
- 合并：由一个项目 Agent 承担多个默认角色的职责，适合范围较小或上下文高度重合的项目；
- 替换：用更符合项目类型、引擎或制作方式的 Agent 接替默认职责；
- 新增：创建根框架没有预设、但项目确实需要的专项 Agent 或管线角色。

项目特化改变的是角色编制，不改变根框架的协作规则。每次编制变更必须：

- 说明每个项目 Agent 继承或承担了哪些通用职责；
- 保证完整生命周期中的必要责任没有无人承担，也没有含糊的重复所有权；
- 定义输入、输出、文件或产物所有权、验收方式、失败回退和人工判断点；
- 继续使用通用 Contract、交接、验证、审计和人工闸门规则；
- 由人类批准会改变决策权、成本、范围或质量责任的编制方案。

根框架中的五个默认 Agent 可以作为项目编制的来源模板，但不能成为限制项目创建专项 Agent 的理由。

项目专属编制由 `AGT-ORG` 项目编制设计 Agent 提出。它读取项目资料和通用责任地图，判断默认 Agent 应当如何保留、拆分、合并、替换或扩展，并输出责任覆盖矩阵、成本、风险和待审批项。它只能设计和建议编制；长期部门与正式岗位的新增、删除或权限变化必须由人类批准，批准后才能绑定已批准的 Agent Preset 并实例化。详细边界见 `agents/project-agent-architect.md`。

## 分层组织模型

根框架采用“人类治理 → 元管理 → 部门管理 → 专项执行”的可伸缩组织模型：

| 层级 | 通用角色 | 核心责任 |
|---|---|---|
| 人类治理 | 项目负责人和人工审批者 | 决定方向、范围、预算、质量取舍、项目编制和关键闸门 |
| 元管理 | 项目编制设计 Agent、项目经理 Agent | 前者设计团队编制，后者负责跨部门优先级、依赖、资源、进度和冲突协调 |
| 部门管理 | 项目按需实例化的部门经理 Agent | 承接项目目标，管理本领域工作，整合部门交付并向项目经理汇报 |
| 专项执行 | 专业 Agent、临时子 Agent 或 Skill 执行者 | 在批准的职责与任务范围内生产具体设计、代码、资产、测试和证据 |

组织层级是通用框架，具体部门不是。根框架提供部门经理的通用职责契约；美术、叙事、关卡、技术、音频或其他部门是否存在，由项目编制方案决定。

工具与生产管线部门同样属于可选项目部门。它负责跨生产环节的编辑器、数据转换、导入导出、稳定映射和往返验证，但不拥有玩法、内容、美术方向或运行时架构决定。小型项目可把这些职责并入技术部门；存在持续跨部门工具需求、独立工具链和维护责任时，才建议独立实例化。参考模板见 `departments/tools-and-production-pipeline.md`。

小型项目可以压缩组织层级：部门经理可以在职责和验收边界清楚时兼任执行者，一个 Agent 也可以承担多个部门责任。项目不得为了形式完整而实例化没有实际职责的管理层。

### 组织对象与运行身份

组织治理必须区分四种对象：Department 是长期组织边界，Agent Preset 是可版本化能力定义，Position 是经过批准的正式岗位，Agent Instance 是一次实际运行身份。“长期 Agent”只是“已批准 Position + 已批准 Agent Preset 版本绑定”的简称，不代表永久运行的进程。

创建或改变 Department、Position 及其权力边界必须事前人工审批；生成草案不授予执行权。已批准岗位在相同绑定下重启不重复审批。临时实例可以在有效授权的数量、成本、权限、期限和层级额度内创建，但必须逐次登记；越界前必须升级，且不能静默转为正式岗位。

上述对象使用不同稳定 ID，改名不改 ID、退出后不复用。组织图只能从结构化对象确定性生成，不能作为事实源或审批依据。完整定义见 `contracts/organization-identity.md`。

### Organization Registry

每个项目拥有独立的 Organization Registry，保存当前已批准 Department、Position、准确 Preset 绑定、Agent Instance 和治理事实。它与 Loop Registry 分离：前者回答“谁构成当前组织并正在运行”，后者回答“哪些生产循环处于什么状态”。Loop Registry 单向引用 Position 或 Instance；联合视图按两个 Registry 的明确水位生成，不保存可能漂移的反向列表。

Organization Event History 是权威历史，Snapshot 必须可以从事件重建。Snapshot 从同一历史物化正式编制、运行实例、治理完整性三类视图。未批准组织变化只存在于 Organization Change Set；Registry 可以记录待审批引用，但不能把建议节点提前混入正式编制。当前组织图、运行图和待审批差异图都是确定性投影，不是事实源。完整边界见 `contracts/organization-registry.md`。

Department 与 Position 使用 `active / suspended / retiring / retired` 的长期生命周期；未批准对象只存在于 Change Set，不使用 `proposed` 状态。Agent Instance 使用 `starting / active / draining / ended` 的运行生命周期，结束后重启必须创建新 ID。Position 空缺、父 Department 暂停和绑定失效属于派生状态，不级联改写生命周期。完整转换与审批规则见 `contracts/organization-lifecycle.md`。

部门经理负责部门产物的整合与初审，但不能替代必须独立执行的 QA、审计或人工体验闸门。生产者与独立验收者需要分离时，不得通过合并角色绕过该要求。

跨部门协作采用“可直连、需留痕、不得越权”的原则：

- 已批准范围内的专业澄清和依赖对接，可以由部门经理或获授权执行者直接沟通；
- 直接协作必须写入 Contract、交接记录或共享依赖记录，使项目经理能够追踪；
- 改变优先级、范围、期限、资源承诺、产物所有权或事实源的事项，必须交由项目经理协调；
- 一个部门不能直接命令另一个部门修改其事实源；无法解决的跨部门冲突由项目经理升级给人类。

## 分级授权与例外升级

组织默认采用“边界内自主、越界才上报”，而不是“所有决定逐项向上审批”。人类、项目经理和部门经理可以把自己拥有且允许委托的部分权力下放给下一层；获得授权的角色在已批准的目标、期限、预算、工具、文件和风险边界内自行决定、验证并留痕。

当事项超出当前授权时，执行者停止受影响的决定并提交选项、证据、影响和建议。直属上级拥有该决定权时即可处理；仍无权限时才继续逐级上报，直至到达有权决定的角色或人工闸门。上报是处理例外的路径，不是每个任务的固定步骤。

每项授权必须记录授权人、被授权人、允许决定的事项、适用范围、约束、有效期、证据要求、撤销条件、上报对象和是否允许继续转授。授权人不能下放自己没有的权力，也不能通过转授绕过独立 QA、审计或人工闸门。完整格式见 `contracts/authority-delegation.md`。

专业审查与审批必须分开：审查判断产物是否符合专业规格，审批判断当前角色是否有权接受取舍或允许状态转换。部门经理可以在授权内完成部门初审，但不能把初审解释为项目级批准或人工体验批准。

## 项目组织生命周期

项目组织不是一次性生成的静态结果，而是在根框架约束下持续校准的循环：

1. 根框架以人类负责人、项目编制设计 Agent 和项目经理职责组成最小启动团队；正式编制获批前，项目经理职责只通过受限 bootstrap workflow 执行，不伪造运行实例；
2. 人类负责人提供已规划的核心玩法、美术方向、大致实现方案、约束、已有资料和明确未知项；
3. 项目经理启动工作流把这些输入整理为项目文档基线，区分 `confirmed / preference / hypothesis / unknown`，登记来源、矛盾、风险与开放问题；
4. 人类负责人确认项目简报准确表达了自己的方向和未知项；只有摘要匹配且 staffing-ready 的简报才能进入编制设计；
5. 项目编制设计 Agent 提出初始部门与 Agent 编制方案，并说明责任覆盖、成本、风险和替代方案；
6. 人类批准后才建立长期 Department 与 Position，并绑定已批准的 Agent Preset 版本；
7. 项目经理运行已批准团队，部门经理组织专项执行；
8. 里程碑变化、长期职责缺口、负载失衡、工具链变化、独立验收冲突或持续存在的临时工作组触发编制复审；
9. 项目经理更新项目简报和变更影响，项目编制设计 Agent 再根据确认后的新基线提出调整方案，经过人工批准后迁移编制；
8. 项目经理恢复生产并继续监测下一次复审信号。

这是一套由 Workflow、Contract、状态和触发条件驱动的多循环机制，不默认新增一个拥有全局决策权的 `multi-loop` Agent。现有管理角色分别承担循环中的组织设计、项目协调、部门执行和人工审批责任，避免权力与职责重叠。

## 可审计组织与人类可视化

项目组织使用一份逻辑 Organization Snapshot 和一条全局有序 Event History。Snapshot 保存当前正式 Department、Position、准确 Preset 绑定、运行实例、临时授权和治理引用；Event History 解释它为何成为当前状态。所有对象使用不可复用的稳定 ID，每个原子 mutation 恰好追加一个类型化 Event，并同时更新全局 revision、事件水位和摘要链。

长期编制变化必须进入 Organization Change Set。项目编制设计 Agent 可以自主生成草案、校验和图，但所有长期 Department、Position、Preset 绑定、权限上限和独立验收关系在应用前都需要人工批准。批准绑定结构化 Change Set 摘要与决策基线，不绑定图片；批准后由独立 apply Event 原子生效，不能把“已批准”解释为“已应用”。

为了兼顾开发速度与项目掌握，临时执行使用“预先批准有限额度 + 创建即登记”的方式：经理可以在 Temporary Grant 明确的 Preset、权限、数量、成本、时长和创建深度内自主实例化，不要求逐实例事前审批；每次实例化仍必须先以 `starting` 进入 Registry，并立即出现在运行视图和 Event History。任何越界在创建前升级审批。

同一结构化事实可以确定性生成三类视图：

- 正式编制图：回答当前有哪些部门、岗位、职责、Preset 和汇报关系；
- 运行实例图：回答哪些正式或临时实例正在运行、依据什么授权以及额度使用；
- 待审批变化图：把一个 Change Set 叠加在当前编制上，区分现有、拟新增、拟修改和拟退出节点。

项目级图显示完整组织，部门经理使用 Department ID 作为 scope 生成本部门及子部门图。Mermaid/SVG 只是只读投影，必须标记 revision、水位和摘要，不能通过编辑图像反向修改 Registry。

## 可插拔扩展边界

根框架把不可替换的治理核心限制在稳定身份、Contract、事件、授权、人工闸门和验收语义。Agent Preset、Skill、Workflow、工具 Provider、引擎 Adapter 和项目覆盖层都可以按项目安装、替换或裁剪；扩展通过带版本与摘要的引用接入，不复制或改写核心事实。

插件版本迁移同样受治理边界约束。版本不一致时项目进入 `read_only`，只有与源/目标基础版本精确匹配的显式 migrator 才能提出变更。迁移计划必须绑定源锁、目标框架摘要、逐文件前后摘要、人工批准摘要、逐字节备份、后置校验与回退路径；plugin lock 最后更新，不能被当作绕过迁移的开关。详细流程见 `workflows/plugin-migration.md`。

这种“能力可插拔、治理不可绕过”的边界允许项目创建专属 Agent 和工具链，也避免某个 Harness、模型、引擎或项目风格成为根框架的硬依赖。任何插件或项目覆盖都不得绕过人工保留权、稳定 ID、Change Set 审批、Event History 或独立验收。

项目启动时不要求完成完整 GDD。初始项目画像只需覆盖项目目标、当前阶段、已知与未知设计、平台与引擎约束、主要内容复杂度、时间与成本约束、已有资料与资产，以及当前最大风险。项目经理主动研究、提供跨专业建议与备选，并与所有者共同敲定方向；负责结构化和追溯，不得把偏好、建议或待验证思路升级成已确认事实；编制获批后，详细 GDD、美术规范、技术设计和测试计划分别由对应领域角色深化。后续事实变化通过项目简报升版与编制复审进入下一轮，而不是要求第一次编制预见整个项目。

## 多循环驱动机制

根框架使用可持久化、可审计的流程机制驱动多个并行或嵌套循环，不把循环控制权集中到一个超级 Agent：

| 组件 | 责任 |
|---|---|
| Loop Contract | 定义本轮循环的目标、责任角色、输入、产物、验收、人工判断、触发器和回退路径 |
| Loop State Machine | 定义当前状态、合法转换、转换条件、阻塞状态和失败返回位置 |
| Loop Registry | 记录项目中存在哪些活动、暂停、阻塞、待审批和已结束循环，以及它们的父子关系与依赖 |
| Loop Coordinator | 检查准入条件，发现阻塞和复审信号，依据已批准转换执行提醒、路由和汇总 |
| Responsible Agents | 完成专业分析、生产、整合和判断，并为状态转换提供证据 |
| Human Gates | 批准方向、长期编制、高成本投入和其他不可委托的判断 |

Loop Coordinator 是流程基础能力，不是新的全局决策者。第一版优先将它实现为项目经理可调用的 Skill 或确定性脚本；只有真实项目证明它需要持续独立上下文和判断边界后，才考虑提升为长期 Agent。

Loop Coordinator 禁止自行批准状态转换、修改项目范围、改变长期编制、裁决领域结论或替代人工闸门。它只能依据已批准的 Contract 和状态机执行确定性检查与路由；缺少条件、存在冲突或转换规则不明确时，必须标记阻塞并交还相应责任角色。

多循环至少包括组织循环、项目循环和部门循环，也可以由具体 Workflow 增加玩法验证、资产生产、技术预研或发布循环。上层循环协调目标和约束，下层循环生产证据与结果；下层发现职责或范围问题时，可以按 Contract 触发上层复审，但不能静默改写上层决定。

### Loop、Task、Review 与 Gate 的分界

只有需要跨多次执行持续保存状态、允许反复修订，并且拥有独立目标、负责人、产物、结束条件和回退路径的生产闭环，才定义为一个 Loop。Loop 可以独立启动、暂停、阻塞、恢复、回退和结束，也必须能够说明每轮迭代相对上一轮改变了什么。

- Task 是 Loop 内的一次具体动作，完成后把产物或证据交回所属 Loop，不单独建立循环状态机；
- Review 检查产物是否符合专业规格，可以要求修订，但本身不拥有项目方向或状态转换批准权；
- Gate 决定是否允许某次状态转换或进入下一阶段，是 Loop 中的决策点，不因为发生审批就自动成为独立 Loop；
- Loop 组织多个 Task、Review 和必要 Gate，直至达到结束条件或按回退规则终止。

若一个事项只执行一次、无需跨轮保存状态，或没有独立负责人、产物和结束条件，应保留为 Task、Review 或 Gate。只有同时存在可重复迭代、持久状态和独立闭环责任时，才在 Loop Registry 中注册为新 Loop。例如，单次调整一个 UI 元素的位置是 Task；“设计输入 → 人工调整 → 结构化导出 → 引擎映射 → 验证 → 返修”在需要反复迭代时才构成 UI 布局 Loop。

### 第一版循环运行规则

- 每个 Loop Contract 必须设置轮次、时间或成本中的至少一种预算。预算耗尽时只能暂停复审或按授权路径升级，不能自动宣告成功，也不能无限继续；
- Review 未通过时，原 Loop 返回执行状态并进入下一轮，记录反馈和相对上一轮的变化，不为同一目标创建新的 Loop；
- Contract 只规定允许的父循环类型、依赖规则和子循环创建条件。具体父子 ID、依赖 ID、当前状态和当前轮次属于运行事实，只记录在 Loop Registry 中。

`contracts/loop-contract.template.yaml` 定义稳定规则；Loop Registry 负责绑定具体项目、Contract 版本、授权记录和运行状态。修改运行状态不得反向改写 Contract，Contract 升版后也不得静默改变正在运行的实例。

### 默认状态机的中断恢复规则

`blocked`、`paused` 和 `waiting_approval` 是中断状态，不是新的迭代。进入其中任一状态时，Registry 必须把进入前的 `ready`、`active` 或 `review` 保存为 `resume_state`，并记录 Contract 版本、输入版本、依赖、授权和预算快照。

中断解除后不能直接继续工作，而要重新检查绑定 Contract、必要输入、依赖、授权、预算和转换证据。全部通过才返回 `resume_state`；复检发现新的阻塞、待审批或主动暂停原因时，可以转到对应中断状态，但继续保留最初的 `resume_state`，不建立嵌套恢复栈，也不增加迭代次数。

审批结果只证明等待事项已有有权决定，不能替代专业审查或完成条件。`waiting_approval` 取得结果后先返回 `resume_state` 并重检；默认状态机只允许从 `review` 进入 `completed`。完整状态与转换规则见 `contracts/loop-state-machine.default.yaml`。

## 按需专业能力

默认编制不把 P6 内容资产生产压缩为单一 Agent。环境美术、角色与动画、UI/UX、VFX、音频、本地化的工具链和验收方式差异较大，具体项目可以根据资产需求设置对应专业 Agent、Skill 或子管线。

当项目需要持续美术方向、多域一致性或独立视觉验收时，可通过编制审批实例化 `AGT-ART-DIRECTOR-TEMPLATE` 与可选美术部门。主美从项目体验与玩法可读性出发，先联网研究并提出至少三条方向，通过 D2 人工选向、D3 代表性引擎基准和 D4 生产冻结后，才把风格圣经和技术 Profile 交给 P6 资产生产。主美拥有 UI 视觉签名和跨域翻译，但不拥有 UI Screen/Flow、布局行为或交互逻辑；后者必须走独立 UI workflow。

专业执行者必须遵守以下边界：

- 只消费已批准的资产需求和技术规格；
- 不自行改变游戏机制、关卡目标或叙事事实；
- 以 Specialist Asset Contract 绑定需求、可编辑 Source、Runtime、权利、版本、导入配方、项目预算实测与返修原因；
- 在 `specialist-asset-production` Loop 内依次通过 A0 需求、A1 Source、A2 Runtime、A3 集成冻结门禁；
- Loop Registry 只保存资产 ID、revision、URI、文件摘要、Contract subject digest 和 Gate 证据，不复制资产正文；
- 由内容设计检查表达是否符合意图，由实现 Agent 检查引擎与性能规格，由测试 Agent 检查集成结果；
- UI Screen/Flow、布局与交互等领域事实源保持只读，资产循环若需改变它们必须另开上游工作流。

## 决策权限

Agent 可以在已批准规格内选择实现方法、生成结构化产物、执行检查和提出修订。以下决定必须由人类批准：

- 项目范围、核心支柱和 `MUST / SHOULD / WON'T`；
- 核心玩法是否值得继续；
- 角色、情绪、节奏、美术方向是否达到目标；
- D2 核心画风选择，以及未委派的 D4 美术生产基线是否批准；
- 灰盒是否冻结并进入高成本内容生产；
- 是否接受破坏性变更、延期、降级或删减；
- 是否允许发布构建成为对外版本。

## 事实源与变更规则

- 已批准的 Contract 和决策记录是工作的事实源，聊天内容不能直接覆盖它们。
- Agent 发现上游矛盾时必须停止受影响步骤，提交变更请求，不得在下游静默修正规格。
- 所有重要对象使用稳定 ID；改名不改 ID，删除保留迁移说明。
- 交接必须附带变更文件、验证证据、风险和未解决问题，不能只说“已完成”。
- 失败必须按 Contract 的回退规则返回负责角色；不得由下游角色越权重写上游决定。

## 适配层边界

通用层只描述玩家体验、内容意图、系统责任、验收和交接。引擎节点、资源类型、脚本语言、导入规则和执行命令属于适配层。

当前 Godot 适配层必须遵守“预置节点优先”：能够在编辑器中稳定表达的节点树、UI、碰撞、动画、相机和关卡结构，应序列化到 `.tscn` 或 `.tres`，不通过运行时脚本临时搭建。

## 共同立项与自主执行控制面（alpha.5）

立项阶段允许项目经理从想法开始，通过跨专业咨询、研究和有界原型与所有者共同形成方向。可先联合准备简报及组织草案，再按依赖应用精确审批。真正的方向/体验选择和组织授权由人类作出；不预签未发生的产物验收。

新增控制对象：

| 对象 | 唯一职责 | 校验与退回 |
| --- | --- | --- |
| Production Charter | 启动范围、19 类领域覆盖、验收、工具/模型、写入、预算、通知和委派 | 绑定实际人类来源和 Project Brief 摘要；越界回立项 |
| Tool Registry | Provider、能力、版本、来源、权限、确定性、回滚 | 源文件 SHA-256 与绑定摘要变化使执行失效 |
| Execution Plan | generate/automate/takeover/decide 模式、固定上下文、DAG、lane、write_set、all-join、自检 | 先授权检查再调度；重叠无序写入禁止 |
| Execution Event | 不可变产物快照、自检、修复、独立审核、成本和完成事实 | JSONL 哈希链、单写锁与原子替换；恢复重放 |
| Production Gate Decision | 指定独立审核者对当前产物和既定标准的判断 | 精确主体和证据摘要；失效回生产者，不自动放行 |

组织 Registry 记录 Agent 实例与正式交接；执行事件记录任务尝试与证据，两者不能互相冒充。Charter 可以授权后续 GATE-2/GATE-3/D4 的规格符合性判断；初始 GATE-0/GATE-1/D2 仍由人类确认。成本按计划预分配且累计检查，不能通过另起同 ID 计划重置。批准的工具绑定加入 Agent Preset 摘要并输出到适配器说明。

默认不因普通技术失败中断所有者：有限自修复后独立复查；跨越授权或用尽恢复路径才提交集中异常包。后续整体方向、范围、组织或外部权限变化仍走原治理路径。真实外部发布需明确目标/成本/条件及 GATE-4；未授权则停在交付包。

本版没有常驻调度器、宿主工具拦截或自动账单采集；哈希证明内容一致性，不证明签名身份或检查语义。实际工具调用、独立判断和费用记账需要执行 Agent 真实完成，后续用真实游戏项目测量一次通过率、人工接管、返工及有效完成。
