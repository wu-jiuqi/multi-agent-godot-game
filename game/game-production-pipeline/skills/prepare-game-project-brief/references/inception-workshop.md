# Collaborative inception workshop

The goal is a project the owner understands and Agents can execute without repeated direction questions. Use these concerns as coverage, not a mandatory interview order. Reuse existing answers and decisions.

| Concern | Work the Agent prepares | Owner-facing decision / evidence |
| --- | --- | --- |
| Player and goal | Audience, fantasy, experience pillars, success and anti-goals | What the player should feel/do; what this project excludes |
| Gameplay | Core loop, verbs, win/fail/recovery, progression, difficulty | Experience hypothesis, representative playable loop, acceptable fallback |
| Content | Narrative role, level structure, content counts, replayability | Content ceiling and priority cuts |
| Art | Distinct visual options, references, readability, production cost | Chosen direction, positive/negative samples, permitted variation; D2 before launch when applicable |
| UI/UX | Main flows, screen/state inventory, input/focus, accessibility | Representative interaction and supported devices; visual approval does not approve behavior |
| Audio | Music/SFX roles, triggers, mix, source policy | Emotional direction and scoped audio list |
| Technology | Engine/platform, architecture, performance, saves, tools, deployment | Feasibility evidence and build constraints; Godot uses preset scenes/nodes first |
| Scope and resources | MUST/SHOULD/WON'T, milestones, critical path, cost estimates | Hard caps, permitted cuts and fallbacks |
| Testing and quality | Acceptance examples, regression scope, playability, independent review | Measurable finish conditions; Agent preference is not human playtest evidence |
| Assets and distribution | Licenses, AI provenance, attribution, localization, store/build needs | Allowed sources/providers and exact external publication/spending scope, if any |
| Organization | Minimal responsibilities, write ownership, independent reviewer, tool needs | Staffing, Skills and budgets approved before production |
| Autonomy | Delegated decisions, escalation triggers, recoverable failures | Charter, notification intent, stop conditions and delivery destination |

For each concern retain status, evidence, recommendation, alternatives, decision owner, chosen boundary, acceptance, and unresolved items. Not-applicable requires a rationale. Put implementation detail in project-owned specifications.

## Discussion

Start with the intended player experience and strongest constraints. Research and propose before asking the owner to solve a specialist problem. Group two or three dependent choices with a recommendation. Use a small sample where words are insufficient. Each answer updates the decision record; do not ask it again unless evidence or approved scope changes.

Independent consultations cover design, technical feasibility, art/UI/audio, and QA/risk. Return disagreements and concrete alternatives, not redundant design documents. The coordinator resolves conflicts inside accepted constraints and brings direction-changing trade-offs to the owner.

## Launch packet

Present a compact overview linking exact subjects and digests: the brief and player/visual direction; prototype/sample results and what remains unproven; scope, acceptance and fallbacks; staffing, Skills, tools and ownership; Production Charter; bounded unknowns with experiment owners and stop conditions.

The owner can approve this packet in one response when all named subjects are concrete and unchanged. Record that response as the source of multiple exact approvals, not blanket authority for future staffing changes or direction revisions.

## Production expectations

After launch, Agents plan, implement, inspect, repair, integrate, test, and prepare delivery within the charter. Greybox/content/art readiness checks can use delegated independent reviewers. Scope/core experience/initial art selection and permissions outside the charter return to the owner. Publication may be preauthorized only for named targets and conditions; otherwise finish the release package and stop that external action.

Notify on meaningful completion, failure requiring owner action, or a boundary decision. Resolved failures belong in the durable log. Continue independent lanes while an exception waits; do not resend an unchanged exception. Persist ready tasks and recovery points if the Codex session stops. This plugin supplies workflow and validation, not a background execution service.
