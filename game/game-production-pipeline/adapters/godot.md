# Godot 适配层 v0.1

本适配层将通用游戏制作 Contract 映射为 Godot 4.x 工程产物。它不修改游戏设计、内容设计或人工闸门，只约束实现方式和技术证据。

## 事实源映射

| 通用产物 | Godot 产物 |
|---|---|
| 玩家行为与输入规格 | `project.godot` 中的 Input Map；不得硬编码按键作为唯一输入 |
| 关卡灰盒 | 可在编辑器中打开和运行的 `.tscn` 场景 |
| 可复用交互对象 | 独立 `.tscn` 场景、必要脚本和配置 Resource |
| 游戏数据与规则配置 | 优先使用自定义 `.tres` Resource；跨工具交换时才用 JSON/YAML |
| UI 结构 | `Control`、Container、Theme 等预置节点与资源 |
| 动画与反馈 | `AnimationPlayer`、`AnimationTree`、Tween、Audio 节点或粒子节点 |
| 自动验证 | 无头启动、脚本检查、测试插件和目标平台导出检查 |

## 预置节点优先规则

以下内容能够在编辑器中稳定配置时，必须序列化到场景或资源：

- 角色、关卡、UI、相机、灯光和碰撞节点树；
- 交互对象的固定组成和默认状态；
- 输入动作、动画轨道、音频总线和主题；
- 固定数量的出生点、触发区、导航区和关卡实体；
- 设计师需要直接观察、摆放或调参的内容。

只有满足下列条件之一，才允许运行时动态生成节点：

- 实例数量由运行时数据决定且无法预置；
- 对象池、弹幕、掉落物等生命周期必须动态管理；
- 程序化生成本身就是已经批准的玩法或生产需求；
- 动态方案有明确的可维护性、性能或工具链优势，并记录理由。

动态生成不能用来隐藏本可由 `.tscn`、`.tres` 或编辑器设置表达的固定结构。

## 场景组织

- 一个场景只封装一个能清楚命名的概念；可复用、可独立测试或多人并行修改的部分拆为子场景。
- 默认使用组合；只有多个变体共享相同结构且主要差异是导出属性时才考虑场景继承。
- 子节点通过信号向上报告事件；父节点通过方法向下驱动子节点。
- 无父子关系的跨场景通信仅在确有需要时使用小型 EventBus，不把业务逻辑塞进 Autoload。
- 关卡场景是组合根，负责摆放和连接实例，不承载所有游戏逻辑。

## 推荐工程边界

具体项目可选择按类型分离或按功能共置，但必须在 P3 Contract 中冻结一种布局。最小目录应能区分：

```text
res://
├─ assets/
├─ scenes/
│  ├─ components/
│  ├─ interactables/
│  ├─ levels/
│  └─ ui/
├─ scripts/
├─ resources/
└─ tests/
```

## 实现前路由

`AGT-GODOT` 在实现具体系统前必须读取匹配的 Godot 领域 Skill。例如：

- 场景树：`scene-organization`
- 输入：`input-handling`
- UI：`godot-ui` 与 `responsive-ui`
- 存档：`save-load`
- 动画：`animation-system`
- 测试：`godot-testing`
- 导出：`export-pipeline`

未找到对应 Skill 时，在交接中记录能力缺口，作为未来 Skill 候选；不得假装已有规范。

## 最低技术证据

根据项目实际命令填入 Contract，不使用本文中的占位命令冒充验证结果。至少提供：

- 项目可被目标 Godot 版本无错误导入；
- 主场景和本次变更场景可无头加载；
- 相关自动测试通过；
- 关键路径可从入口完成；
- 适用时完成目标平台导出检查；
- 场景结构遵守预置节点优先和职责边界。
