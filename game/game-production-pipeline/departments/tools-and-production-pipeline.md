# 工具与生产管线部门模板

## 定位

工具与生产管线部门是项目可以按需实例化的可选部门，不属于所有游戏项目必须常驻的根框架编制。它为设计、美术、关卡、UI、音频、技术和测试部门提供编辑、转换、导入导出、数据映射与往返验证工具。

小型项目应优先把这些职责交给技术部门中的专项 Agent、Skill 或临时工作组；只有需求持续出现、存在独立工具链和产物所有权、需要专门验收或已经成为多部门瓶颈时，项目编制设计 Agent 才应建议把它设为独立部门。

## 成立条件

满足下列多项条件时，可以提议实例化本部门：

- 多个生产部门反复提出编辑器、批处理、导入导出或格式转换需求；
- 手工调整难以稳定映射回游戏工程，已经产生重复劳动或数据漂移；
- 工具需求拥有独立的需求队列、版本、使用者和维护周期；
- 工具错误可能批量污染资产、场景或事实源，需要独立验证与回滚；
- 专项工具能力已经明显超出技术部门的临时支持容量。

只有经项目编制流程和人工批准后，才能把该模板实例化为长期独立部门。条件消失时，应合并回技术部门或撤销，避免为一次性工具保留管理层。

## 核心责任

- 接收带有使用者、输入、目标输出、验收、权限和回滚要求的工具需求 Contract；
- 判断应复用现有工具、扩展已有工具，还是新建项目专属工具；
- 设计可人工操作的编辑界面、稳定数据结构、导入导出和迁移方案；
- 维护设计数据与引擎数据之间的稳定 ID、版本和映射规则；
- 验证“导入—编辑—导出—引擎集成—再次打开”的往返一致性；
- 提供使用说明、失败诊断、兼容性记录和可恢复的回滚路径；
- 将跨项目反复验证有效的能力提交为根框架 Skill、模板或工具候选，不直接污染通用核心。

## 不拥有

- 玩法、叙事、视觉风格、布局意图或体验质量的最终决定；
- 其他部门事实源的内容所有权；
- 未经技术负责人同意改变运行时架构、资源格式或构建策略的权力；
- 未经编制审批把一次性工具任务扩张为长期 Agent 或部门的权力。

工具部门负责让已批准意图可编辑、可交换、可验证，不替代需求部门决定“应该设计成什么”。

## UI 布局工具参考闭环

1. UI 或内容设计角色提交已初审的设计图、布局意图、目标平台和工具需求 Contract；
2. 工具部门判断复用、扩展或新建方案，并在超出授权额度时上报成本与风险；
3. 工具提供可视化调整能力，并保持元素稳定 ID、层级和约束；
4. 人类调整位置、尺寸或约束后，导出结构化布局数据；
5. 引擎适配层验证并映射到项目场景或资源；
6. 设计角色检查表达是否符合意图，技术角色检查集成与性能，QA 检查往返和回归；
7. 失败时根据错误归属返回设计输入、工具实现、数据映射或引擎集成步骤。

布局数据不能只包含绝对的 `x / y / width / height`。根据项目需要还应覆盖稳定 ID、父子层级、参考分辨率、锚点、枢轴、伸缩与安全区约束、层级顺序、资源引用、版本，以及本地化或响应式规则。

## 事实源与往返规则

- 项目必须指定布局数据或引擎场景中的一个作为唯一可编辑事实源；
- 如果两者都允许编辑，必须提供明确的合并、冲突检测和迁移规则；
- 导出物必须带版本和来源，未知字段、丢失 ID 或不兼容版本不得静默覆盖；
- 工具写入前应生成可审查变更或备份，批量失败能够回滚；
- 对 Godot 项目，优先使用 `EditorPlugin`、`@tool` 和预置 `.tscn` / `.tres` 资源完成编辑期映射；固定 UI 不应默认在运行时由脚本临时搭建。

## 最小交付证据

- 工具需求 Contract 与授权记录；
- 可复现的输入样例、操作步骤和结构化输出；
- 数据结构、稳定 ID、版本与迁移说明；
- 往返一致性、异常输入和回滚测试；
- 设计、技术与 QA 各自职责范围内的验收结果；
- 已知限制、维护责任与停用条件。
