# 六部门、P2P 与产品经理原型工作流验证方案

状态：`partially-executed / live-pilot-blocked`。本轮已运行 V0 的设施检查、V1/V2 的受控子集和 V4 的故障替身；尚未运行正式项目编制、真实审批或 Penpot 文件纵切片。V3 真实试点因当前用户令牌没有连接 Penpot 实例而阻塞，V4 的真实 P2P 成本对照尚未运行。

设计基线：`3c8906c0f2c763c46be9349f7d7afeb5ee104e27`。执行时另行记录实际 commit、插件来源、模型配置和工具能力证据；基线改变后重新判断受影响用例。

## 1. 要回答的问题

| 假设 | 需要观察的事实 | 不能据此直接推出的结论 |
|---|---|---|
| 固定六槽位不会强制运行六个经理 | 实际实例、模型调用和加载日志；未启用槽位零调用 | 目录、Skill 描述和路由元数据完全没有上下文开销 |
| 部门经理能够直接协作 | 真实发件人、收件人、投递/响应记录及咨询事件一致 | 在文档里画了 P2P 连线就具备 P2P 运行能力 |
| 项目经理能形成可信 PRD/GDD | 结论能追溯到领域意见、证据和人类决定，冲突未被隐去 | 项目经理可以代替领域事实 owner 或人类批准 |
| 产品经理能调用原型 Skill 完成交接 | 真实 Penpot 可编辑产物、Screen/Flow 映射、走查和评审 | MCP 返回成功或截图存在就表示原型完成 |
| P2P 有实际收益 | 同条件对照中的质量、转述量、调用成本、耗时及返工 | 单次成功就证明 P2P 更便宜、更快或稳定 |

验证分别输出：组织和权限边界是否成立、产品交接是否可用、成本收益是否值得保留。三种结论不互相替代。

## 2. 当前证据与需要补齐的能力

本轮补齐了咨询事件实例校验与确定性重放、产品原型交接实例校验、受控组织/工具替身和运行报告。完整回归目前为 250 项测试通过；这些结果只证明本地设施与受控沙盒行为，不替代真实 Registry、宿主权限、审批记录或 Penpot 交付证据。运行证据见 [`docs/validation-runs/2026-10-04-six-department-product-prototype/`](../validation-runs/2026-10-04-six-department-product-prototype/)；真实 Penpot 纵切片仍为 `blocked`。

当前 [组织扩展校验器](../../game/game-production-pipeline/scripts/validate_organization_extensions.py) 主要检查模板字段与声明；[对应测试](../../game/game-production-pipeline/tests/test_organization_extensions.py) 主要检查模板和文档标记。`validate_consultation` 要求模板列出七种事件枚举，不能直接当成单条真实事件的校验器。`validate_handoff` 不核实真实审批记录、源文件摘要或远端原型。现有 Organization Registry 等模块提供部分可复用校验，但不自动覆盖新咨询链路。

| 前置项 | 拟补内容 | 完成判据 |
|---|---|---|
| 实例校验 | 区分模板与实值实例；检查合法单事件、嵌套类型、ID、参与者、收件人、状态和引用 | 有效实例通过；缺字段、非法类型、占位符、未知 ID 返回明确错误，不能崩溃或误通过 |
| 咨询记录器与重放 | sequence、水位、mutation 幂等、摘要链、咨询状态、发送/接收证据关联 | 重放还原相同咨询结果；同 mutation 同 payload 无第二份事实，不同 payload 拒绝 |
| 实际调用审计 | 记录 spawn、实例身份、消息投递、模型/工具调用、写入范围和结束/回收 | 调用可与授权、Position/Instance 和事件对账；不能仅靠 Agent 自报 |
| 产品交接校验 | 解析本地来源、revision、内容摘要、审批对象和主体、工具范围、屏幕/流程及评审引用 | 假批准、旧批准、过期来源、缺必要评审不能形成可实施交接 |
| 受控工具替身 | 模拟断连、只读、写成功但响应超时、重试和能力缺失 | 可复现工具故障，并观察写入前后状态 |

这些是验证设施的待办，不是已实现的生产能力。先补最小可用校验、记录与观测，再运行行为试点；缺设施时该项为 `blocked`，不能把书面推演写成通过。

执行前需要固定以下语义，作为设施实现任务，不在本次文档中默默修改共享契约：

- 咨询模板使用 `consultation-event-canonical-json-v1`，但 `CONSULT-008` 引用了 `registry-event-canonical-json-v1`。建议明确为独立标识、复用明确指定的规范化算法，并用固定输入/摘要向量验证；在语义统一前，V0 只能为 `blocked`，不能通过；同步模板、记录器与重放器。
- 产品方向、原型输入和交付证据应有明确的审批摘要范围。新增截图、响应或交付证据不能无故使已批准且未改变的方向失效；修改范围或选定方向必须使相关审批失效。需要先约定哪些字段进入各摘要，避免整包自引用或用更新后的状态反向签批准。
- 交接字段中的 `slot_id` 统一使用目录里的 `slot:*`；组织映射状态与单次咨询参与状态分开记录。`unused` 不代表能力缺失，`not_requested` 也不代表该职责已经验收。
- 现有文件契约没有拦截全部宿主工具的能力。涉及“阻止越权”的用例必须核查真正执行路径；若仅能事后发现修改，记录为“检测到越权”，该预防性用例仍失败。

## 3. 试点范围与执行环境

建议用“一个小游戏的新手任务选择与结算原型”作为验证夹具。名称和主题只是测试素材，不作为真实游戏立项决定；已有明确需求的小功能也可等量替换。

固定范围：3 个关键屏幕（任务入口、任务详情、结果反馈），1 个目标视口，1 条主流程，以及返回、取消、失败重试三个分支。包含正常、禁用、成功、错误等约定组件状态。功能需求用稳定 ID 列出，并在执行前给每条定义观察结果。

原型采用状态模拟，不声称已实现游戏逻辑。首轮不包含完整游戏、Godot 构建或发布；若后续验证引擎交接，单独追加场景实施与构建证据。

输入包预置：目标与边界、产品身份候选或已有决定、简单 UX/视觉来源、待验证假设、一个故意保留的产品冲突。评审者另持检查清单，例如“预算无法同时支持复杂动画和全部屏幕”“某条玩家偏好尚未确认”。检查清单不作为生产 Agent 的答案输入。

运行在隔离项目和专用 Penpot 文件中。合成夹具、模拟批准和工具替身全部标记为 synthetic，只验证机械行为；真实审批必须来自已有有效记录或实际人类决定，不能复制夹具记录冒充。

执行清单至少记录：

- `run_id`、代码 commit、插件路径/摘要、模型与推理配置、工具能力快照、时区与开始时间；确认读取的是新增源码，不能误用未更新的 alpha.11 安装缓存。
- 项目与可写路径、源文件摘要、组织 Snapshot/Change Set、Preset/Skill 版本与有效授权；已有摘要未变的授权复用，不重复申请。
- 实际并行容量、消息投递方式、允许的模型/工具、调用或 token/费用上限、墙钟时限、局部重试上限；没有批准额度就保留未定项，不把“六个经理”理解成无限并发。
- 建议每个议题最多两轮 peer 讨论、同一可恢复操作最多一次局部重试；超限仍有冲突则汇总升级。该建议须与项目既有上限取更严格者。
- 生产者与独立评审者身份；同一执行实例不能给自己的结果做最终独立评审。

## 4. 验证阶段

V0～V4 仅是本方案的验证编号，不新增或替代生产体系的 GATE-0～GATE-4。

| 阶段 | 输入与执行 | 证据 | 退出标准与失败回退 |
|---|---|---|---|
| V0：基线与设施 | 固定源码；运行现有回归；补齐最小实例校验、摘要语义、记录器与工具替身 | 命令/退出码/日志、有效与无效夹具、固定摘要向量 | 必需检查通过；设施属于 `facility_implementation_required`。设施未实现，或摘要语义未定，V1～V4 对应项为 `blocked/not_run`，不能宣称试点通过；回框架维护者 |
| V1：槽位与生命周期 | 执行下面的三组组织场景，核对提案、批准、apply、实例与回收 | 前后 Snapshot、事件、调用和文件摘要差异 | 未授权物化/调用为零；按需启用、QA 独立性和授权到期行为可复核；失败回组织设计/调度负责人 |
| V2：咨询到产品包 | 部门答复、真实 peer 消息、项目经理整合、独立检查及必要人类判断 | 咨询历史、投递回执、PRD/GDD、来源矩阵、冲突与决定记录 | 必需意见和关键决定全部可追溯；阻断冲突未解决则不能进入依赖它的交接；事实问题回领域 owner，取舍回项目经理/人类 |
| V3：Penpot 纵切片 | 产品经理调用原型 Skill；真实工具读前写、写后读、连接与走查流程 | 工具调用、可编辑文件、节点映射、快照、分支记录和专业评审 | 所有必需流程完成，必要评审通过；若 MCP/宿主不可用则为 `blocked/not_run`，工具替身通过不能升级为真实交接通过；工具故障回工具 owner，结构回 UI/UX，视觉回主美 |
| V4：恢复、对照和复核 | 注入故障、重放/恢复、需求变更；同条件比较协调方式；独立复核证据 | 故障报告、恢复点、对照原始数据、变更影响报告和最终评审 | 硬门槛全通过可标“试点通过”；效率无证据则单独标未验证；失败回对应 owner |

顺序为 V0 → V1 → V2 → V3 → V4。V4 中权限、摘要与超时故障先在替身环境验证，再选择可恢复的场景在专用真实文件复核。

## 5. 三组组织与协作场景

| 场景 | 槽位配置 | 重点断言 |
|---|---|---|
| S1：目录存在、任务未开始 | 六槽位均 unused | Registry 中不出现新增部门、岗位或实例；六经理调用均为 0。若启动协调器才记录其开销；冷启动不强制启动项目经理，只记录目录加载/审计开销 |
| S2：小型产品原型 | 策划、美术、QA 按职责参与；程序/音频/工具经理默认不唤起，由项目经理/协调事件记录不需咨询的理由，不要求不存在的实例自证 | 产品经理可在已批准工具范围内直接编排 Penpot Skill；使用 Penpot 不自动等于启动工具经理；发现技术依赖再按既有授权增补咨询 |
| S3：完整部门协作与职责合并 | 在合成任务中为六域提供真实问题，分别激活；另建程序+工具合并、音频 unused、临时专业评审的组织变体 | 逻辑参与六域不要求六实例同时运行；合并保留事实与验收责任；QA 不并入生产者；临时授权到期无新调用，已有工作按契约暂停/回收 |

S3 只验证六域覆盖与调度边界，不能用强行让六经理参与小任务的成本代表默认运行成本。若宿主容量不足，分批或按依赖调度，记录峰值并发和等待耗时。

P2P 正常路径：项目经理发起咨询 → 已激活经理回答 → 依赖双方直接澄清或挑战 → 项目经理生成来源可追溯的整合草案 → 独立检查 → 所需人类决定 → 固化咨询结论。

人工检查至少包含：产品身份/范围是否接受、核心体验假设是否值得验证、跨部门取舍是否接受、必要视觉方向是否批准。分别引用现有 GATE-0/GATE-1/D2 或有效的有界原型授权。咨询 `closed` 只表示本轮记录闭合，不表示建议获批。

PRD/GDD 的关键结论定义为影响需求、产品身份、范围、验收、技术承诺和跨部门依赖的条目。每条记录来源事件/产物、revision/digest、状态、责任人和决定引用。经理超时可完成“部分汇总”，但必要事实仍阻塞时不能标整包通过。

## 6. Penpot 验证与证据

1. 检查项目 `tool:penpot-mcp` 的真实连接、能力及允许范围，执行一次只读查询；不从用户过去的 Dot 验证推断本次环境一定可用。
2. 读取专用文件，记录现有页面、节点和版本或可用状态指纹；创建文件的许可、目的地和范围也应在运行包中可查。
3. 先完成一个代表屏幕与组件状态，经检查后扩展到三个屏幕，保留稳定 Screen/Flow ID 和本地映射。
4. 通过宿主实际支持的 MCP 操作或有记录的浏览器交互走查主流程及三个分支。仅检查链接字段属于结构证据；无法执行的必要交互标记 blocked。
5. 独立 UI/UX 与视觉评审检查目标清楚、反馈明确、可返回、错误恢复和视觉一致性。产品所有者进行原型任务走查并记录观察；一次走查不等于统计用户研究。
6. 相同输入再次执行，检查已有屏幕/组件/连线没有重复创建；改变一项输入时仅修改受影响产物，必要批准重新匹配。

每次交付保存：真实 file/page/shape ID、实际返回的版本或状态指纹、视口、可编辑文件引用、本地快照及摘要、`screen_id → frame` 映射、`flow_id → 起点/动作/终点/观察结果`、工具调用 ID、生产者和 reviewer、未支持交互与返工项。缺版本字段如实记录，不能猜测。

`implementation_ready` 要求当前输入、必要专业评审与适用审批均有效，只代表设计可交接；产品体验人类结论、Godot 运行验收和发布批准分别记录。

## 7. 必做失败注入

| ID | 注入 | 期望行为与回退 owner |
|---|---|---|
| F01 | 缺批准、只有 approved_pending_apply 或 Grant 已到期 | 不建立未授权正式编制、不启动/新增越权调用；回组织/授权负责人 |
| F02 | 非法 slot、事件类型、收件人、错类型嵌套数据或自然语言占位符 | 明确返回校验错误且无业务写入；回记录生产者 |
| F03 | 重复 mutation；同 mutation 携带不同 payload | 前者幂等，后者拒绝；不能产生双事实；回咨询记录器 |
| F04 | 两个写入者读取相同 sequence 后提交 | 只有合法提交取得下一水位；过期提交拒绝并刷新重试；回记录器 |
| F05 | 事件摘要/前驱链或角色授权被篡改 | 中止受影响咨询、保留原始证据；从最后可信记录恢复；回框架维护者 |
| F06 | 部门要求直接修改他域事实、覆盖 QA 意见或扩大预算 | 宿主能拦截时才判预防通过；只能事后发现时分别记录 detection pass、prevention fail；保存两方意见并升级，回项目经理/人类，QA 意见不能被覆盖 |
| F07 | 必需经理超时或反复失败 | 有限恢复后保留 blocked/unknown，不编造答复；回项目经理调整咨询；必要领域未覆盖时禁止整体通过 |
| F08 | 策划坚持复杂动画，美术/技术指出超预算 | 摘要保留冲突、方案和代价，交有权者决定；禁止写成“一致同意” |
| F09 | 人类未回复、拒绝，或 Agent 假冒人类批准 | 保持待定/拒绝并拒绝假批准；回具体决定 owner |
| F10 | 批准后改变范围、来源、组织授权或工具范围 | 旧证据仅作历史；受影响批准和交接重新检查；不强制重做无关已验证内容 |
| F11 | Penpot 写入成功但响应超时 | 先只读检查已生效节点再决定局部重试；无法确认时 blocked，不盲目重建；回工具 owner |
| F12 | Penpot 断连、只读权限、缺必要交互能力 | 写前停止或保留部分真实产物；不伪造 URL/截图/成功；回工具 owner |
| F13 | 同输入重复运行或执行者中断后恢复 | 稳定映射保持，无重复节点和竞争流程；读取恢复点后继续；回原型执行者 |
| F14 | 原型链接错误、缺关键状态或必需评审未过 | 保持 review_pending/rework，不升为 implementation_ready；结构回 UI/UX，视觉回主美 |

每例统一核对：是否检测到、状态/原因是否准确、业务副作用是否符合预期、原始证据是否保留、回退责任人与重试条件是否明确。

对于写入前拒绝的场景，Registry 与受保护事实源前后摘要必须一致，允许追加审计记录。F11/F13 等已产生合法部分结果的场景，记录预期部分差异和恢复结果，不能要求假装从未写入，也不能直接回滚覆盖并发的人工作品。多文件或远端事务能力若不存在，应记录限制并验证补偿/暂停，不能仅凭模板声明“原子”。

## 8. 验收标准与指标

| 指标 | 首轮标准 | 证据/计算方式 |
|---|---|---|
| 未启用槽位调用 | 0 | 调用日志按槽位、实际 Instance 对账；不能以配置值代替观测 |
| 未授权写入/批准/实例 | 0 | 授权与执行轨迹、文件/Registry/远端差异；Agent 口头拒绝但实际已写入仍失败 |
| 活跃槽位响应处置覆盖率 | 100%（流程覆盖，不是业务通过） | 有 response 或明确 not_applicable/blocked 的必要槽位数 ÷ 必要槽位数；关键必需意见不得停留在 blocked/unknown，除非人类明确接受风险 |
| 关键决定追溯率 | 100% | 有有效来源和所需决定记录的关键条目 ÷ 冻结的关键条目集 |
| 必需屏幕映射覆盖率 | 100% | 有唯一预期映射和证据的屏幕 ÷ 需求清单中的必需屏幕 |
| 必需流程走查覆盖率 | 100% 且均符合预期 | 主流程和必需分支的真实执行结果；缺能力不能移入 optional 来缩小分母 |
| 假证据/隐藏冲突/未知误标确认 | 0 | 独立 reviewer 核对输入、原始事件及摘要 |
| 重放与重复运行 | 对已记录事件做 deterministic replay 且结果一致；重复业务结果 0 | 重放不能重新调用 LLM；重复 Agent 执行不要求文本逐字一致，只要求稳定 ID、远端对象和事件事实不重复 |
| 故障恢复 | 必做故障符合预期，恢复在额度内 | F01～F14 逐项记录；未执行为 not_run，缺证据为 blocked |
| 人工与专业评审 | 适用的必要评审均明确通过 | 真实主体、对象、摘要、时间和结论；技术 pass 不能代签人工 Gate |

质量评分另设五个维度：范围准确、事实与假设区分、冲突处理、原型可理解性、交接可实施性。每项 0～2 分：0=关键缺失，1=需返工，2=证据支持且满足要求。建议首轮至少 8/10 且无单项为 0；无论总分多少都不能抵消硬门槛失败。运行前冻结评分说明，由独立评审者逐项举证。

## 9. P2P 与成本对照实验

使用同一输入包、模型/推理配置、预算、活跃槽位、工具能力、输出要求与评审标准，只改变沟通路由：

- A：部门之间的问题经项目经理转述；
- B：依赖双方直接通信、保留记录，项目经理接收摘要并整合。

先只比较咨询到 PRD/GDD 阶段，避免 Penpot 工具延迟混入沟通效果。每组建议独立运行 3 次，共 3 对；交替执行 A/B、使用隔离上下文，复用同一份授权输入而非从上轮模型答案继续。人工答复发生变化的配对单独标注，不纳入“同条件”比较。预算不足时减少运行次数并标记样本局限，不暗示具有统计显著性。

记录原始样本和中位数/范围：总调用数、输入/输出与缓存 token（可得时）、实际费用（可得时）、总耗时、等待人类时间、项目经理转述次数、peer 消息与讨论轮数、独立评审分数、返工次数。宿主没有 token/费用数据时写 unavailable；调用数只能作代理指标，不能换算成已知费用。小样本不报告有误导性的 p95。

保留 P2P 的建议依据：全部硬门槛满足，且没有相对 A 的硬门槛回归；转述量、返工或代理执行耗时的变化作为并列结果报告，只有在样本量和预先约定的非劣效容差足够时才讨论收益。若质量更好但调用更贵，应报告这个取舍；若没有收益，保留有冲突时才启用 P2P 的策略，不强行得出全面启用结论。当前 n=3 只报告中位数和范围，不做统计显著性结论。

另对“目录未加载”与“只加载六槽位元数据”做只读对照，记录上下文/耗时差值；把目录元数据成本与真正启动六经理的成本分开。

## 10. 证据包、结果与执行顺序

建议存入隔离目标项目的 `game-pipeline/execution/validation/<run_id>/`，不把真实项目答案、审批或运行状态写入插件模板目录：

```text
manifest.yaml                版本、授权、配置、预算和原始证据索引
baseline/                    受保护输入/Registry 前态及摘要
consultations/               原始事件、消息投递、领域意见和整合映射
calls/                       可获得的实际模型、实例、工具调用记录
product/                     PRD/GDD、决策矩阵、prototype intent 和 handoff
penpot/                      屏幕映射、快照、截图、流程走查和工具状态
failures/                    F01～F14 的注入、观测、差异与恢复结果
reviews/                     独立评审、人类决定引用、A/B 数据与最终报告
```

每个用例结果包含：ID、输入摘要、预期、实际、执行方式（static/synthetic/live）、证据引用、生产者/reviewer、起止时间、成本可得性、失败 owner、恢复条件、状态。敏感令牌不进入证据包。

采用现有评审结果 `pass / revise / blocked / awaiting_human`，未执行另记 `not_run`。负向用例中“正确拒绝越权”可判该测试 pass，但被拒绝的业务任务仍是 blocked/rejected，两种状态分栏保存。

执行顺序与责任：

1. 框架维护者补 V0 设施并对无效实例做故障验证；独立 reviewer 复核，复用现有校验器能覆盖的部分。
2. 组织负责人和项目经理完成 V1 三种场景，核查实际宿主通信与并发能力。
3. 项目经理、产品经理和已激活经理完成 V2 产品包，准备具体审批对象；人类只对其保留判断作决定。
4. 产品经理调用 Penpot Skill 完成 V3；UI/UX、主美及独立 reviewer 验证真实产物。
5. 框架维护者和独立 reviewer 完成 V4 恢复及对照，输出能力结论与成本结论。
6. 第一轮仅标“该试点通过”；再用不同功能和一次需求变更重复验证后，讨论新 Alpha 发布。稳定性声明需更多真实重复证据。

首轮启动所需具体信息留到执行包中填写：隔离项目路径、目标 Penpot 文件/工作区、实际工具入口、已有效的人类决定和预算。它们不影响本方案设计完成，但缺失时不得宣称已完成真实试点。
